# 本番前の負荷テスト

`scripts/load-test.mjs` は、ダミー参加者（ボット）を 150 体動かして、本番と同じ通信をさせるスクリプトです。
各ボットは本物のスマホと同じように動きます。

1. `/api/join` で参加登録する（数秒の間にばらけて一斉に登録）
2. Firestore の `game/state` と自分の `participants/{id}` をリアルタイム購読する
3. 出題されたら、制限時間内のランダムなタイミングで `/api/answer` に回答する（約20%は途中で選び直し、約2%はわざと締め切り後に送って無効になることを確認する）
4. 問題の合間に、一部のボットが通信を切断して再接続し、最新の状態に戻れるかを確認する

`--auto-host` を付けると、司会者の操作（受付締め切り→出題→締め切り→正解発表→次へ→終了）も自動で行います。1人で本番と同じ流れを通して試験できます。

## ⚠ 無料枠についての注意

テストは本物の Firestore に読み書きします。150体×5問で、**読み取り約5,000回・書き込み約2,000回・削除約1,000回**を使います（Spark プランの無料枠は1日あたり読み取り5万回・書き込み2万回・削除2万回）。

- **おすすめ：負荷テスト・リハーサル専用の Firebase プロジェクトを別に作る**（無料）。SETUP.md の手順1〜5を同じように行い、テスト用の値で Vercel にもう1つプロジェクトを作るか、Vercel の **Preview 環境**の環境変数にテスト用の値を設定します。
- 本番用のプロジェクトで試す場合は、**本番当日には実施せず**、前日までに1〜2回にとどめてください。
- 上限に達すると、課金はされずにその日の読み書きが失敗するようになります（日本時間の16時〜17時ごろにリセット）。Firebase コンソールの「使用量」タブで消費量を確認できます。
- テストの最初に**ゲームがリセット**され、終了後もボットの参加者が残ります。**本番前には必ず管理画面で「ゲームをリセット」してください。**

## 実行方法

### 1. 準備

```bash
cd survival-quiz
npm install
```

テスト対象の値を書いた環境変数ファイルを用意します（例：`.env.loadtest`。Git にはコミットされません）。

```bash
# .env.loadtest
NEXT_PUBLIC_FIREBASE_API_KEY=...
NEXT_PUBLIC_FIREBASE_PROJECT_ID=...
NEXT_PUBLIC_FIREBASE_APP_ID=...
ADMIN_PASSWORD=...        # --auto-host で使用（テスト対象のサイトに設定したパスワード）
```

### 2-a. 公開済みのサイトに対して自動進行で試験する（推奨）

```bash
node --env-file=.env.loadtest scripts/load-test.mjs \
  --base-url https://<テスト用のURL>.vercel.app \
  --bots 150 --auto-host --rounds 5 --seed-questions
```

- `--seed-questions`：登録済みの問題が `--rounds` より少ない場合、ダミー問題を追加します（**既存の問題の後ろに追加されます**。本番用の問題を登録済みのプロジェクトでは付けないでください）。
- 本番と同じ問題で試す場合は `--seed-questions` を付けず、`--rounds` を問題数以下にします。

### 2-b. 手動で進行しながら試験する（リハーサル向け）

ボットだけを動かし、進行は人が管理画面から行います。スクリーンの表示や司会の操作感を確認するのに向いています。

```bash
node --env-file=.env.loadtest scripts/load-test.mjs --base-url https://<URL> --bots 150
```

1. ボットの参加登録が終わったら、管理画面から通常どおり進行します（実際のスマホで一緒に参加しても構いません）。
2. 手動進行ではボットは正解を知らないため、50%の確率でランダムに回答します。
3. 終わったら `Ctrl+C` で停止すると、計測結果が表示されます。

### 2-c. ローカルのエミュレーターで試験する（無料枠を消費しない）

```bash
cp .env.emulator .env.local
npm run emulators                                  # ターミナル1
npm run build && npm start                         # ターミナル2
node --env-file=.env.local scripts/load-test.mjs --bots 150 --auto-host --rounds 5 --seed-questions   # ターミナル3
```

ロジックの確認や、コードを変更した後の回帰テストに使えます（ネットワークの遅延は本番より小さく出ます）。
なお、エミュレーターは書き込みを1件ずつ順番に処理するため、`--join-spread 0`（150人が完全に同時に登録）にすると参加登録 API が2〜4秒かかります。本物の Firestore では並列に処理されるので、この数値は本番の目安にはなりません。

## オプション一覧

| オプション | 既定値 | 説明 |
| --- | --- | --- |
| `--base-url` | `http://localhost:3000` | テスト対象の URL |
| `--bots` | 150 | ボット数（本番の想定より多め、例えば 200 で余裕を確認するのも有効） |
| `--auto-host` | なし | 司会者の操作も自動で行う（`ADMIN_PASSWORD` が必要） |
| `--rounds` | 5 | 自動進行で出題する問題数 |
| `--accuracy` | 0.8 | 自動進行時の正答率。`0` にすると毎問「全員不正解→全員復活」を試せます |
| `--join-spread` | 5000 | 参加登録を何ミリ秒の間にばらけさせるか。`0` で完全に同時 |
| `--churn` | 0.1 | 問題の合間に通信を切断→再接続するボットの割合 |
| `--no-reset` | なし | 自動進行時、開始前にゲームをリセットしない |
| `--seed-questions` | なし | 問題が足りなければダミー問題を追加する |

## 注意点

- 1台の PC から150本の接続を張るため、テストする PC の回線や CPU が先に詰まることがあります。結果が悪いときは、`--bots 75` で2台の PC から同時に実行して切り分けてください（2台で動かす場合、`--auto-host` は1台だけに付けます）。
- 実際のスマホは会場の回線を経由するため、ここで測る遅延より大きくなることがあります。可能なら、会場の Wi-Fi で数台の実機も一緒に参加させてください。
- Vercel の無料プランでは、しばらくアクセスがないと最初のリクエストが遅くなる（コールドスタート）ことがあります。本番開始の数分前に管理画面やスクリーンを開いておけば解消します。
